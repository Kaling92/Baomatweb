# Reproducing the supplied thesis before evaluating improvements

## What can and cannot be reproduced from this repository

The supplied source is Tekeste Fekadu's February 2025 Addis Ababa Institute of Technology thesis, *Investigating Malicious Capabilities of Android Malwares that Utilize Accessibility Services*. It is not the IJFMR paper named in the original request. The PDF is copied into `papers/` for source tracking.

The thesis contains partial appendix scripts and reported aggregate results, so its workflow can be reconstructed in stages. It does **not** provide the `base_patterns_opt.csv` or `callgraph_flowdroid_opt.csv` files referenced in Appendix F, the source/sink definition file used by FlowDroid, the APK corpus or complete sample hashes, a complete TinyBERT training source, or the definitions for the model initialization/training helpers used in Appendix G. The PDF's text extraction also damages code formatting. Consequently, the exact reported 1,497-pattern dataset and 97.66% TinyBERT result cannot be reproduced from this repository alone. A rerun using newly obtained samples is a **methodological reproduction**, not an exact replication; record every deviation and never present it as an exact recreation.

The appendices and method chapter also conflict in ways that must be resolved before claiming faithful replication. The manual-review subset is described as 12 samples in Chapter 3 and 21 samples in Chapter 5. A capability result uses 199 samples where other sections report 207. The methods describe agglomerative clustering, while Appendix F includes DBSCAN references and multiple, partly overlapping similarity-labeling procedures. Appendix G's training code uses a random stratified row split rather than grouping related samples by malware family. The TinyBERT model/tokenizer identifier and training helpers are not supplied. These are source reproducibility issues, not choices this repository silently fills in.

## Phase 1: acquire and pin the research tools

Use a dedicated analysis VM, not a personal Android phone or the Windows host that contains personal data. Take a clean snapshot, encrypt the virtual disk, disable clipboard/host-folder sharing, and do not sign into personal accounts. Keep APKs in a separate, access-controlled sample directory. Do not install or run malware on the Android emulator. The APK operations below are static decoding/decompilation only. Confirm that your institution permits the sample sources and handling procedure.

Install Android Studio from [developer.android.com/studio](https://developer.android.com/studio). In Android Studio's SDK Manager, install an Android SDK Platform matching the study's selected API levels and Android SDK Platform-Tools. The existing lab PoC is separate from the thesis classifier; an emulator is only needed for the controlled observer demonstration, not for the thesis's original static analysis. For SDK command-line management, use the current Android SDK Manager documentation at [developer.android.com/tools/sdkmanager](https://developer.android.com/tools/sdkmanager).

Install a JDK supported by the selected Android Studio/Gradle release. FlowDroid's upstream build instructions require JDK 11 or later; use a supported JDK distribution and record its exact version. Install Python 3.10 or 3.11 in a separate virtual environment for legacy ML/decompiler dependencies, then pin every resolved package version in a lock file before running experiments. The thesis does not pin Python, PyTorch, Transformers, XGBoost, FlowDroid, or Android tool versions, so a new installation cannot be assumed bit-for-bit equivalent to the original environment.

On a Windows research VM, Python setup can start with `py -3.11 -m venv .venv` followed by `.\.venv\Scripts\Activate.ps1` and `python -m pip install --upgrade pip`. The appendix workflow indicates dependencies including NumPy, pandas, scikit-learn, XGBoost, PyTorch, Transformers, Sentence-Transformers, and an APK parser such as Androguard. Install compatible versions in that environment, then record the resolved versions with `python -m pip freeze > requirements-lock.txt`. Do not install the ML stack into the Android SDK or system Python. GPU acceleration is optional for the research code; record CPU/GPU, CUDA, batch size, and deterministic settings.

Download Apktool from its [official releases](https://github.com/iBotPeaches/Apktool/releases) and follow its [official installation guide](https://apktool.org/docs/install). On Windows, put the release JAR and official wrapper in a dedicated tools directory, add that directory to the VM's PATH, open a new PowerShell session, and confirm `apktool --version`. Decode one authorized, known-benign test APK first with `apktool d -f -o ..\data\derived\apktool\<sample-id> ..\data\raw\apks\<sample>.apk`. This validates the tool install without executing the APK.

Download JADX from its [official releases](https://github.com/skylot/jadx/releases). Extract the Windows release ZIP into a versioned directory. Use `bin\jadx.bat --version` to verify the CLI, `bin\jadx-gui.bat` to open a known-benign sample for manual review, or `bin\jadx.bat -d ..\data\derived\jadx\<sample-id> ..\data\raw\apks\<sample>.apk` for static decompilation. JADX warns that some methods cannot be fully decompiled; retain the original DEX/Smali view and mark decompilation failures rather than treating missing Java output as absent behavior.

Obtain the FlowDroid command-line JAR from the [official FlowDroid releases](https://github.com/secure-software-engineering/FlowDroid/releases), or build it from the official [FlowDroid repository](https://github.com/secure-software-engineering/FlowDroid). The upstream CLI form is `java -jar soot-infoflow-cmd-jar-with-dependencies.jar -a <sample.apk> -p <Android-SDK>\platforms -s <SourcesAndSinks.txt>`. A valid source/sink definition is essential: do not substitute an unrelated default and describe the result as the thesis result. Run the command on each authorized sample, preserve stdout/stderr and exit code, and place outputs under a per-sample derived directory. The source thesis does not publish its precise source/sink file or full extraction script, so matching its 42,910 candidate patterns depends on obtaining those missing inputs.

For consistency with the readiness checker, place the FlowDroid CLI JAR at `tools\flowdroid\soot-infoflow-cmd-jar-with-dependencies.jar`, or pass its actual path with `--flowdroid-jar`. Once the missing source/sink definitions are available, a PowerShell invocation has this form: `java -jar .\tools\flowdroid\soot-infoflow-cmd-jar-with-dependencies.jar -a .\data\raw\apks\<sample>.apk -p "$env:LOCALAPPDATA\Android\Sdk\platforms" -s .\data\replication\SourcesAndSinks.txt`. Confirm the flags against the version's help/release notes and use the Android platform level appropriate to each sample.

JEB is commercial software; obtain it from [PNF Software](https://www.pnfsoftware.com/) under the institution's license. The thesis mentions Kavanoz but does not provide a version, source link, or installation artifact. Do not download similarly named binaries from unofficial mirrors. Ask the thesis author or supervisor for the exact version and provenance, or record it as an unavailable component and continue only with a clearly labeled alternative workflow.

## Phase 2: collect inputs and establish provenance

Do not fetch executable malware samples onto the ordinary workstation. Obtain samples only from a source approved by the institution and the supervisor, inside the isolated research VM. The thesis names vx-underground and a public GitHub collection as sources, but their mention is not an endorsement, an assurance of current availability, or a substitute for institutional approval. Do not upload samples to public scanning services; uploading can disclose samples or research data. If reputation checks are authorized, query existing hash records only and keep API credentials outside source code and logs.

Create `data/raw/apks/` for legally obtained samples, `data/replication/` for authorized label/callgraph/source-sink files, and `data/derived/` for tool outputs. Preserve a manifest with sample ID, SHA-256, source/date, family attribution if known, license/approval status, tool versions, and processing outcome. The raw APK corpus, original 134/1,497 labeled CSV files, and any API keys are deliberately not included in this repository. The expected layout is described in [`../data/README.md`](../data/README.md). Use the readiness script from the workspace root:

```powershell
python .\tools\replication_readiness.py
```

The script only checks file paths and tool versions; it never parses or executes an APK. It should report blocked until the original pattern CSVs, FlowDroid source/sink definitions, permitted APK corpus, Java, Apktool, JADX, and Android SDK platforms are present.

## Phase 3: reproduce the static-analysis and capability counts

For each authorized APK, compute and record SHA-256 before analysis. Run Apktool to decode its Manifest, resources, and Smali into `data/derived/apktool/<sample-id>/`. Determine whether a declared service has the exact `android.permission.BIND_ACCESSIBILITY_SERVICE` service permission, not merely a similarly named string elsewhere in the APK. Parse each `res/xml*` Accessibility Service configuration, preserving the source resource path and version-qualified directory. Record declared event types, feedback type, accessibility flags, `canRetrieveWindowContent`, and other capability fields separately from dynamically configured values found in Smali. A declared capability is evidence of configuration, not evidence that the capability was used maliciously.

Use JADX/JEB and the decoded Smali to manually inspect the service class and event-handling paths for each sampled APK. Keep a structured evidence ledger that links every behavior label to a specific sample hash, method or call path, and reviewer decision. Do not collect real UI contents or execute malware to complete this static phase. Run FlowDroid only when the sample, Android platform JARs, and correct sources/sinks are available. Preserve failures as explicit outcomes because the thesis reports that 86 of 207 samples could not be processed successfully.

The thesis reports 1,800 collected APKs, 738 valid, 207 accessibility-service samples, 134 manually labeled API patterns, 121 FlowDroid-processed samples, 42,910 candidate patterns, and 1,497 patterns after labeling. Compare reproduced counts only after defining the denominator and exclusions at each stage. Report discrepancies, especially the 12-versus-21 manual subset and 199-versus-207 capability denominator, instead of tuning filters until numbers happen to match.

## Phase 4: reconstruct the pattern and classifier experiments

Request from the author or supervisor the exact `base_patterns_opt.csv`, `callgraph_flowdroid_opt.csv`, source/sink file, API-call extraction program, TinyBERT model and tokenizer identifiers, omitted initialization/training functions, parameter values, and split assignments or random seeds. The PDF's Appendix F references `all-MiniLM-L6-v2` and `paraphrase-MiniLM-L6-v2`, PCA with 50 components, a similarity threshold of 0.7, fuzzy-ratio matching, and DBSCAN variables. The chapter text instead describes agglomerative clustering. Reconstructing a single procedure without the missing original code is a deviation; run the documented method and appendix-derived method as separately named variants if exact clarification is unavailable.

For the model baseline, use the original labeled API-pattern CSV only after validating its schema and label counts. The paper reports TinyBERT with AdamW, learning rate 5e-5, batch size 10, five epochs, and 512-token inputs; it reports XGBoost with TF-IDF, learning rate 0.1, maximum depth 6, and 100 estimators. Record the exact tokenizer, model checkpoint, package versions, hardware, seed, truncation/chunking, and class-weight handling. The paper's Appendix G uses `StratifiedKFold(n_splits=10, shuffle=True, random_state=42)` on rows; reproduce that as the **paper-style baseline** if the input data becomes available, but also preserve predictions for later analysis. Do not call row-level folds a family-independent generalization test.

Compare results with the reported TinyBERT accuracy/F1 near 97.66%/97.67% and XGBoost accuracy/F1 near 90.38%/90.00%. A mismatch is meaningful only if dataset, label distribution, preprocessing, model checkpoint, and evaluation procedure have been checked. Do not claim exact replication based only on similar aggregate accuracy.

## Phase 5: freeze the reproduction, then evaluate improvements

Archive the baseline commands, inputs' hashes, tool versions, environment, exclusions, intermediate CSVs, model checkpoints, fold-level predictions, and metrics before changing the method. That frozen baseline provides the comparison point. Only then evaluate improvements: group folds by family/package, hold out a time/source cohort, include benign accessibility applications, report false-positive rates and per-class metrics, validate similarity-generated labels independently, and stratify by Android API level. Keep these results under a separate experiment identifier so the changes are not mistaken for reproduction.

The Android module under `poc/` is a safe runtime teaching aid restricted to its own synthetic app. It is not part of the thesis's static APK-analysis or TinyBERT experiment and cannot substitute for the missing original dataset or training code.
